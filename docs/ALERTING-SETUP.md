# Alerting Setup Guide

Containarium uses Prometheus-style alerting with vmalert + Alertmanager, relayed through the daemon to webhook destinations (Slack, Zulip, etc.).

## Architecture

```
VictoriaMetrics ──→ vmalert ──→ Alertmanager ──→ daemon /internal/alert-relay ──→ Webhook (Slack/Zulip/...)
   (metrics)         (rules)     (grouping/      (HMAC-signed,                   (final destination)
                                  throttling)     records deliveries to DB)
```

**Why the daemon relay?** It records every webhook attempt to PostgreSQL (`webhook_deliveries` table), masks credentials in API responses, and lets us swap webhook destinations without restarting Alertmanager.

## Built-in Alert Rules

Located in vmalert config (auto-generated by daemon at startup). Current groups:

### `container_alerts`
| Alert | Severity | Trigger |
|-------|----------|---------|
| `ContainerHighMemory` | warning | Container uses >3.5GB memory for 5+ minutes |
| `ContainerStopped` | info | Any user container stopped for 10+ minutes |
| `ContainerHighCPU` | warning | Container CPU >90% for 10+ minutes |

### `pentest_alerts`
| Alert | Severity | Trigger |
|-------|----------|---------|
| `PentestCriticalFindings` | critical | Any open critical-severity Trivy/pentest findings |
| `PentestHighFindings` | warning | More than 3 open high-severity findings |

### `bridge_dns_alerts`
Series come from the bridge DNS reconciler (`containarium bridge-dns status`).
They exist only on hosts that run it, and only after its first pass, so other
hosts never alert. A bridge with no record, where the operator has not opted in
to creating one, is not "out of sync" and does not fire `BridgeDNSOutOfSync`.

| Alert | Severity | Trigger |
|-------|----------|---------|
| `BridgeDNSOutOfSync` | critical | `bridge_dns_in_sync == 0` for 10+ minutes: boxes may resolve the base domain to an address that does not answer |
| `BridgeDNSReconcilerStale` | warning | No reconcile pass finished for 5+ minutes (passes run at least every minute) |
| `BridgeDNSDriftRepeating` | warning | The record was found drifted more than 3 times in an hour: something keeps changing it |

### `system_alerts`
| Alert | Severity | Trigger |
|-------|----------|---------|
| `BackendUnhealthy` | critical | A backend (peer) is unhealthy for 5+ minutes |
| `DiskSpaceLow` | warning | Disk usage >85% on any container |
| `DiskSpaceCritical` | critical | Disk usage >95% on any container |

## Configuring Webhook Destination

### Zulip Setup

1. **Create webhook bot** in Zulip:
   - Settings → Bots → Add new bot
   - Bot type: **Incoming webhook**
   - Name: `containarium-alerts`
   - Note the API key

2. **Create or pick a stream** (e.g., `Op-Room`)

3. **Webhook URL format**:
   ```
   https://YOUR-ORG.zulipchat.com/api/v1/external/alertmanager?api_key=BOT_API_KEY&stream=STREAM_NAME&topic=TOPIC_NAME
   ```

4. **Configure in Containarium**:
   ```bash
   TOKEN=$(containarium token generate --username admin --roles admin --expiry 1h --secret-file /etc/containarium/jwt.secret --raw)

   curl -X PUT \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"webhookUrl": "https://YOUR-ORG.zulipchat.com/api/v1/external/alertmanager?api_key=KEY&stream=Op-Room&topic=alerts"}' \
     https://<cluster>.example.com/v1/system/alerting
   ```

5. **Send test alert**:
   ```bash
   curl -X POST -H "Authorization: Bearer $TOKEN" \
     https://<cluster>.example.com/v1/system/alerting/test
   ```

   You should see a test message in your Zulip stream.

### Slack Setup

1. Create incoming webhook at https://api.slack.com/apps → Incoming Webhooks
2. Pick a channel and copy the URL (`https://hooks.slack.com/services/T.../B.../xxx`)
3. Configure same as Zulip but with the Slack URL

## Credential-expiry alert

The daemon also sends one alert of its own straight to the same webhook,
without going through vmalert/Alertmanager, so it works on hosts with no
VictoriaMetrics container.

- **When:** a skill box's coding-engine sign-in becomes unhealthy. For Claude,
  alert only when its access token has expired for **more than 24 hours**,
  or an actual runtime run failed with a typed authentication error. A
  single recently expired token is refreshable and does not alert, even
  across multiple sweeps. Every 15 minutes the daemon probes each running
  skill box. The manual `containarium agent credential-status` command
  continues to report raw access-token expiry. The alert fires once per flip
  into `CODE_CREDENTIAL_SOURCE_EXPIRED`, never again while the box stays
  expired, and again only after a fresh sign-in has expired in turn. The
  first time the daemon sees a box that is already expired counts as a flip.
- **Restart-safe:** the last-seen state is kept in Postgres
  (`code_credential_watch_state`), so restarting the daemon does not re-send.
  Without Postgres the watch is disabled.
- **Destination:** the webhook URL and secret set through
  `PUT /v1/system/alerting`, signed with the same
  `X-Containarium-Signature: sha256=<hex>` HMAC header. Each delivery is
  recorded in `webhook_deliveries` with source `credential-watch`. No
  webhook configured means the alert is logged and not sent.
- **Payload** (names only; the credential value never leaves the box):

  ```json
  {
    "alert": "CodeCredentialExpired",
    "skill_id": "<skill-id>",
    "box": "agent-<skill-id>-container",
    "engine": "AGENT_ENGINE_CLAUDE",
    "credential_source": "CODE_CREDENTIAL_SOURCE_EXPIRED",
    "previous_source": "CODE_CREDENTIAL_SOURCE_INTERACTIVE",
    "observed_at": "2026-10-07T12:00:00Z"
  }
  ```

  `previous_source` is `CODE_CREDENTIAL_SOURCE_UNSPECIFIED` when the box
  was already expired the first time it was seen.

The runtime records **OAuth-sourced** authentication failures as metadata-only
failure episodes in `~/.local/state/containarium/claude-auth-state.json` (0600,
private parent directory). It never reads credential values. SDK account/init
metadata identifies OAuth, API-key, and third-party/gateway sources; cached
credential-file existence is not evidence of the source a run used. A failure
before any trustworthy source metadata is available remains an unknown-source
run error and does not change interactive sign-in state.

`is_error=true` never proves recovery, regardless of the SDK result subtype.
Only a newer successful OAuth run recovers OAuth health. Key-backed runs and
unrelated failures cannot recover it. `flock` serializes metadata updates across
runtime processes; run generations prevent older completions from overwriting
newer authentication outcomes. Recovery does **not** delete pending evidence.

The daemon consumes episode IDs through the private
`agent-runtime-credential-state snapshot/ack` protocol, persists them in
`code_credential_watch_episodes`, then acknowledges the guest. Failed database
writes or guest acknowledgement retain evidence for retry. Repeated failures
within one unhealthy episode deduplicate; failure/recovery/failure between
sweeps still yields separate transition alerts. Episode IDs survive restarts.
Delivery keeps the existing persist-before-notify posture: a claimed episode is
not re-invoked after restart, while the notifier's existing HTTP retries remain.
A crash between the database claim and webhook invocation can lose delivery;
a lost HTTP response can also cause a retry at the receiver. There is no
exactly-once external webhook guarantee.

### Upgrading existing skill boxes

Existing boxes are reused without rerunning recipe `post_start`. Updating the
daemon alone does not install the new runtime/helper in those boxes.

1. Update the daemon first. Existing credential-state rows are preserved; the
   episode table is additive. Older runtimes retain the timestamp-based 24h
   policy without authentication-failure evidence.
2. Pause new runs/delegations for each reused box and stop its existing
   serve/poll runtime processes through the normal service lifecycle. Keep
   `~/.local/state/containarium` and the existing sign-in files intact.
3. Inside that box, rerun the matching release's `install-agent-runtime.sh`
   using the same `PREFIX`, with `RELEASE=<reviewed-release-tag>` and a fresh
   versioned `APP_DIR` (for example `/opt/agent-runtime-<release>`). This installs
   both launchers and checks for Linux `flock`; no credentials are supplied to
   the installer. Resume using the same box user/HOME the daemon probes.
4. Run `agent-runtime-credential-state begin` to verify locking and durable
   writes, then `agent-runtime-credential-state snapshot` to verify protocol
   version 1. Output contains only generation/episode metadata. Resume runs.
5. Verify one synthetic transition through the configured test webhook on a
   throwaway guest before rolling out broadly. A helper that exists but fails
   is logged; timestamp-based alerts continue independently and no episodes
   are acknowledged until the durable store succeeds.

The release bundle verifier requires both credential-state modules. Unknown
protocol versions are rejected. Do not delete pending state as an upgrade or
rollback shortcut. Older daemons ignore the new helper/state; their older
alert policy is not upgraded by deploying the runtime alone.

See [SECURITY-ENCRYPTION-AT-REST.md](SECURITY-ENCRYPTION-AT-REST.md#coding-agent-sign-in-credentials-inside-a-box)
for exactly what expiry metadata the probe reads.

## External URL (Alert Source Links)

Each alert message includes a "Source" link. By default vmalert uses its internal Docker hostname (unreachable from outside). Override with `-external.url`:

The daemon configures vmalert with:
```
-external.url=https://<cluster>.example.com
```

Alert links become:
```
https://<cluster>.example.com/vmalert/alert?group_id=...&alert_id=...
```

## Throttling & Repeat Intervals

Alertmanager config (auto-generated):

```yaml
route:
  receiver: 'webhook'
  group_by: ['alertname', 'severity']
  group_wait: 30s        # Wait 30s for more alerts in same group
  group_interval: 5m     # Send updates every 5min while group is active
  repeat_interval: 4h    # Re-send unchanged alerts every 4h (warning/info)
  routes:
    - match:
        severity: critical
      repeat_interval: 1h  # Critical alerts re-send every hour
```

**Why don't I see alerts immediately?**
- New alerts wait `group_wait: 30s` before first send
- Active alerts only re-send every `repeat_interval` (1h critical, 4h others)
- To force re-send: `incus exec containarium-core-victoriametrics -- systemctl restart alertmanager`

## Adding Custom Alert Rules

Custom rules can be added via the API:
```bash
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{
    "name": "MyCustomAlert",
    "expr": "container_memory_usage_bytes{container_name=\"my-app\"} > 8e9",
    "duration": "5m",
    "severity": "warning",
    "summary": "My app using high memory",
    "description": "Memory usage > 8GB for 5+ minutes"
  }' \
  https://<cluster>.example.com/v1/alerts
```

List rules:
```bash
curl -H "Authorization: Bearer $TOKEN" https://<cluster>.example.com/v1/alerts
```

## Troubleshooting

### Alerts firing in UI but not arriving in webhook

**Symptom**: Web UI Monitoring tab shows firing alerts, but webhook destination receives nothing.

**Likely cause**: vmalert can't reach Alertmanager. The notifier URL must include the `/alertmanager` path prefix.

Check:
```bash
incus exec containarium-core-victoriametrics -- grep notifier /etc/systemd/system/vmalert.service
```

Should show:
```
-notifier.url=http://localhost:9093/alertmanager
```

If it shows `http://localhost:9093` only, alerts go to a 404. Fix:
```bash
incus exec containarium-core-victoriametrics -- sed -i 's|http://localhost:9093 |http://localhost:9093/alertmanager |' /etc/systemd/system/vmalert.service
incus exec containarium-core-victoriametrics -- systemctl daemon-reload
incus exec containarium-core-victoriametrics -- systemctl restart vmalert
```

### Webhook configured but test fails

Check the daemon logs:
```bash
journalctl -u containarium --since "5 min ago" | grep -i "webhook\|relay"
```

Common issues:
- Webhook URL syntax errors (missing `?` or `&` separators)
- Zulip stream doesn't exist or bot has no access
- Slack webhook revoked/disabled

### Alert links show internal hostname

vmalert needs `-external.url`. Check:
```bash
incus exec containarium-core-victoriametrics -- grep external /etc/systemd/system/vmalert.service
```

If missing, the daemon should set it on next restart. Manual fix:
```bash
incus exec containarium-core-victoriametrics -- sed -i '/-notifier.url/a\  -external.url=https://YOUR-DOMAIN \\' /etc/systemd/system/vmalert.service
incus exec containarium-core-victoriametrics -- systemctl daemon-reload
incus exec containarium-core-victoriametrics -- systemctl restart vmalert
```

### Old alerts won't go away

Alertmanager remembers fired alerts. To clear all state:
```bash
incus exec containarium-core-victoriametrics -- systemctl restart alertmanager
```
